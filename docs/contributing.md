# Contributing

The site is four static pages: TypeScript and Preact, built with Vite. Every change goes
through the same checks:

```sh
npm ci --ignore-scripts  # install exactly what package-lock.json lists, run no install scripts
npm run typecheck        # TypeScript, strict; a misspelled UI string key fails here
npm test                 # unit tests: engine, data, translations, store, built CSP
npm run build            # static site in dist/
npm run preview          # serve dist/ locally to look at it
```

The data tests are written to explain what is wrong: the failure message names
the profession, subject or language and the rule it breaks.

CI runs more checks on every pull request; [ci.md](ci.md) lists them and how to
run them locally. Two of them concern every contributor.

## Commits: your GitHub noreply address, no trailers

The repository is public, and so is every address in its history. CI
(`npm run check:commits`) accepts a commit only when:

- its author and committer e-mail are your own GitHub noreply address. GitHub
  shows it under Settings, Emails, "Keep my email addresses private"; it has
  the form `<id>+<username>` at `users.noreply.github.com`. Set it for this
  repository with `git config user.email` followed by that address. Besides
  personal noreply addresses, only GitHub's own noreply address (merges made
  on github.com) and Dependabot are accepted; other bot accounts are not;
- the message contains no other e-mail address, in the text or in a trailer;
- the message has no trailers. Co-author trailers (`Co-Authored-By`) are not
  accepted: the check knows one value, the maintainer's own. `Signed-off-by`
  is accepted only as Dependabot's sign-off, so do not use `git commit -s`.
  Any other trailer (`Reviewed-by`, `Change-Id` and so on) fails as well;
- no line looks like a generated-by footer: a line that starts with
  "Generated with" or "Generated by", or any line with a robot emoji. The
  check also refuses ordinary prose that happens to match (for example a
  sentence that mentions that emoji): reword the message.

A commit that fails needs a new author or message (`git commit --amend
--reset-author`, or `git rebase` for older commits) before the pull request
can be merged.

## Add a file

The repository holds only what belongs to the program. `npm run check:tree`
fails for any tracked file that is not on the list in `scripts/check-tree.mjs`
(root files, the docs and the collector's fixture files by name, and patterns
for `src/`, `scripts/`, `e2e/` and the collector's modules and tests). When
you add a file outside those patterns, add its path to the list in the same
pull request, so the reviewer sees it. In a pull request the check
also reads every commit: a file that is not on the list must not appear in any
of them, even if a later commit deletes it, so rewrite the branch rather than
deleting such a file afterwards. The same check refuses symlinks, submodules,
executable files, files that are not UTF-8 text (the one exception is the
animation, see below), and e-mail addresses, paths from your computer, private
keys, private network addresses or local host names in any tracked file. Keep
personal settings, notes and scratch files out of the repository; your global
git ignore file is the place for their patterns.

## Check before every push

Rewriting a branch does not take back what you have already pushed. CI checks
the commits that a pull request holds when its run starts. A version of your
branch that no CI run got to check, and that you then force-pushed away, is
never checked: for example one pushed before you opened the pull request (CI
does not run on pushes to branches other than `main`), one pushed while the
pull request had a merge conflict (GitHub runs no `pull_request` workflow
then), or one whose run your next push cancelled before the checks. Its
commits can stay on GitHub all the same, reachable by their hash. So run the
history checks yourself before every push:

```sh
npm run check:tree -- --range origin/main HEAD
npm run check:commits -- origin/main HEAD
```

## The collector

`collector/` holds the collector, which will turn open data sources into
numbers for the site: Python 3.14, the standard library only, nothing to
install. [collector.md](collector.md) describes it. After a change there, run
its tests, the gate's self-test and the check of the emitted file:

```sh
python3.14 -I -S -B -m unittest discover -s collector/tests -t collector
python3.14 -I -S -B collector/run.py selftest
python3.14 -I -S -B collector/run.py emit --check --set fixture
```

Keep its files ASCII text with no executable bit, give no module the name of
a standard library module, and write planted test samples (addresses, markup,
invisible characters, phrasing of an instruction) as fragments put together
at run time, never as text in the file.

## Re-record the animation

`docs/demo.gif`, the animation at the top of the README, is recorded from the
built site by `scripts/record-demo.mjs`. Record it again after a change that
shows on the page:

```sh
npm run build
npx playwright install chromium   # once
node scripts/record-demo.mjs      # writes docs/demo.gif
```

The script also needs ffmpeg on your PATH (install it with your package
manager). It plays a fixed scenario in English at 1280x800, a short tour of
the four pages (Maths up in the building, Dutch down among the doors, then a
school level and a profile on the onderbouw page, and a level, a profile and
an exam subject on the bovenbouw page), takes one screenshot per step and
writes a GIF 880 pixels wide, without metadata. It fails with a
message, and leaves the old file as it was, when something it needs is
missing, when a page reports an error, when the scenario no longer shows
what it is meant to (more professions open after Maths, fewer doors after
Dutch, other counts on the onderbouw page after the choices, more doors open
on the bovenbouw page after the exam subject; after a data change, adjust the
grades and the choices at the top of the script), or when the result does not
pass the parse of `npm run check:tree`. That parse keeps out the metadata that tools
write and anything appended, and caps the file at 2 MiB, 880x880 pixels, 400
frames and 60 s for one pass; it does not see what the pixels show, nor data
hidden on purpose in them, in the colour table or in the format's free
fields. Look at the new file before you commit it, and update the description
of the animation in the README if the scenario changed. In a pull request
every version of the file that a commit writes is parsed as well, so if one
fails, rewrite the branch rather than committing a fix on top, and run the
check before you push (see "Check before every push"). Ctrl-C stops the
script and removes its screenshots.

## Add a profession

Professions live in `src/data/professions.ts`, grouped by floor. The order
inside a floor is the order of the tiles on screen.

| Field    | What it is |
|----------|------------|
| `id`     | lower case, `a-z`, `0-9` and `-`; unique. It appears in shared links (`g=`), so do not rename an existing one |
| `level`  | floor: 0 no diploma, 1 mbo 2-3, 2 mbo 4, 3 hbo, 4 wo |
| `emoji`  | one emoji for the tile |
| `name`   | `L(nl, en, ua)`: the full name in the three languages |
| `short`  | optional `L(...)`: a shorter name for tiles and hints |
| `about`  | `L(...)`: one or two sentences a 10-year-old understands |
| `needs`  | `n(subject, min)` pairs: level 0 needs none (or minimums of 3 at most); other floors 2 to 5 subjects with a minimum from 4 to 9 |
| `pay`    | 1 to 5, demo scale shown as euro signs |
| `family` | ladder name; a profession that is not on a ladder uses its own id |
| `rung`   | position on the ladder, counting from 1 |
| `field`  | field of work, the group of its door in the doors view (`deuren.html`): `care`, `technology`, `making`, `nature` or `people` (`FIELDS` in `src/engine/types.ts`) |
| `vmbo`   | mbo professions (levels 1 and 2) only: the vmbo direction that fits best in the onderbouw view: `techniek`, `zorg`, `economie` or `groen`. A fit, never a requirement |
| `admission` | hbo and wo professions (levels 3 and 4) only: `{ direct, bridge }`, the havo/vwo profiles (`nt`, `ng`, `em`, `cm`) that admit directly, and per other profile the one extra exam subject that closes the gap (`wiskunde-a`, `wiskunde-b`, `natuurkunde`, `scheikunde`, `biologie`). A profile in neither list needs another profile. `direct` is empty only when every admitting profile needs an extra subject. `source` names the Ratho row the rule follows, with its intake (`havo` or `vwo`), the four cells as written (`cells`) and, next to each, the cell as a typed rule (`rules`, used by the bovenbouw view: `*` admits, `#` no right, or groups of subjects of which each needs one; write a row with `ratho(...)` and `needs(...)`; `notListed(...)` for a programme without a row, where both are `null`), and, where a footnote lets profiles catch up subjects in the first year, `catchUp` (see [sources.md](sources.md)); when a row does not settle, write the stricter reading and `verified: false`. hbo professions also have `vwo`, the rule for vwo pupils (`{ direct, bridge, source }` from section 4 of Bijlage B); wo professions have none |

Rules the tests check (`src/data/data.test.ts`):

- **Ladders.** Rungs of a family are numbered 1, 2, 3 ... without gaps and
  never step down a floor. Each rung needs at least what the rung below
  needs: every subject of the lower rung is listed again, with the same or a
  higher minimum. The engine relies on this, so a ladder always reads "the
  next step asks for a bit more".
- **Floors.** Each floor has 5 to 8 tiles. The layout shows 8 tiles per row:
  a ninth tile would start a second row and the whole building would no
  longer fit on a phone screen.
- **Fields.** Each field holds 4 to 8 professions (one row of doors on a
  phone) and spans at least three floors, so that no field of the doors view
  stands for a level in disguise.
- **Key subjects.** Every subject must be the highest requirement of at least
  two professions, so every slider matters for something.
- **Count.** The test pins the number of professions (36). When you add or
  remove one, change that number in the test and in `README.md` in the same
  change.
- **Onderbouw data.** Every mbo profession names a vmbo direction and every
  hbo and wo profession has admission data with at least one profile that
  admits, directly or with one extra subject; nothing else has either. Every
  hbo profession has a rule for vwo pupils too, and no wo profession has one.
  Every profile and subject named exists, and no profile is both direct and
  bridged. Every rule has a source with the Ratho version and its intake; a
  verified rule names its bijlage (A for wo, B for hbo) and programme, and
  the data agrees with its cells: `*` is direct, a cell with one subject or
  a choice is a bridge to one of those subjects, a cell with `+` or `#` is
  closed, and no row means every profile. The test pins the counts on the
  profile buttons: a change in the data changes them, so update them on
  purpose.
- **Bovenbouw data.** Every row with cells has a typed rule next to each
  cell, and a row without cells has none. The test reads each cell's text
  with its own small reader and checks that the typed rule says the same, that
  the typed rules agree with `direct` and `bridge` (`*` is direct, a rule of
  one group bridges to one of its subjects), and that every group holds at
  least one of the five exam subjects, so the boxes on the page can meet it.
  `src/engine/exam.test.ts` pins the counts on the bovenbouw profile buttons
  for several sets of subjects; update them on purpose too.

The states (open, nearly there, locked) and the minimum average per floor are
described in [methodology.md](methodology.md). They are engine rules: change
them only together with `src/engine/scoring.ts` and its tests.

## Add a subject

1. Add the id to `SUBJECT_IDS` in `src/engine/types.ts`, at the end.
2. Add the subject, with the same id and in the same position, to
   `src/data/subjects.ts` (`emoji`, `name`, optional `short`).
3. Use it in the `needs` of at least two professions, as the highest
   requirement (see "Key subjects").

The link format stores one character per subject in `SUBJECT_IDS` order
(`s=6666666666`). A new subject makes old links one character short, and
those fall back to the default grades. Update the tests that spell out a full
`s=` value (`src/engine/hash.test.ts`, `src/ui/store.test.ts`).

## Add a language

1. Add the code to `LANGS` in `src/engine/types.ts`. The language switch in
   the header follows this list.
2. Copy `src/i18n/en.json` to the new file and translate every value. Keep
   the `{placeholders}` exactly as they are. Strings with a count
   (`tile.ariaSteps`, `card.focusAverage`, `doors.open`, `doors.stepOpens`,
   `doors.next`) need one entry per plural category
   of the language, as `Intl.PluralRules` lists them (`.one`, `.few`, `.many`,
   `.other`).
3. Register the file in `MESSAGES` and the HTML language tag in `HTML_LANG`
   (`src/i18n/index.ts`), and map the browser language in `detectLang`.
4. Add the new language to `L(...)` in `src/data/subjects.ts` and to every
   `L(...)` call in `src/data/professions.ts`.

`src/i18n/i18n.test.ts` fails until every key exists with the same
placeholders, and until the plural strings match the categories that
`Intl.PluralRules` reports for the language. `src/data/data.test.ts` fails
until every name and description exists in every language.

Limits today:

- Plural strings work for languages whose categories are `one` and `other`,
  optionally with `few` and/or `many`: for example Dutch, English, German,
  Turkish (one, other), French, Spanish, Portuguese (one, many, other),
  Polish, Ukrainian (one, few, many, other). A language with `zero` or `two`
  (Arabic, Welsh, Hebrew) or without `one` (Chinese, Japanese, Korean) needs
  the translation types in `src/i18n/index.ts` and the key check in
  `src/i18n/i18n.test.ts` extended first.
- Right-to-left languages are not supported yet: the layout assumes
  left-to-right text.

## Text style

Short sentences that a child of 10 understands. British English. In
Ukrainian, no Russianisms. Use " - " (a hyphen with spaces) as the dash.

## Privacy

Do not add storage, analytics, external fonts or network requests: each page
promises it stores and sends nothing (see the Privacy section in
[methodology.md](methodology.md)). `src/csp.test.ts` builds the site and
checks that the Content-Security-Policy of every page allows no network access.
